# Experimental NES target

BootHush has an experimental headless Nintendo Entertainment System target for caller-supplied NROM cartridges. It includes a CPU, an approximate PPU renderer and timing model, OAM DMA, scheduled controller input, and approximate audio capture. It is **not a complete NES emulator**: cycle-accurate PPU/APU behavior, save RAM, other mappers, and full CPU conformance are missing. Graphics, audio and timing have known approximations. Do not treat results as physical-hardware validation.

```powershell
& 'C:\Repos\boothush\out\windows\boothush.exe' --machine nes `
  --rom 'C:\path\to\original-test.nes' --steps 100000 --timeout-ms 5000 `
  --until-pc 0x800e --inspect 0x10:1
```

Use your own original or appropriately licensed cartridge. BootHush does not supply game ROMs or fetch them. The program address in the example is fixture-specific. `--steps` is an instruction bound from 1 to 100,000,000, **not CPU cycles**. `--timeout-ms` is required and checked at instruction boundaries. `--until-pc` is optional and stops before executing that address, including the reset address; an unreached condition returns `condition_not_met` and exit 1. Without it, `step_limit` is a successful bounded stop (exit 0), not proof of guest success. A fault or timeout exits 1; invalid input or an unsupported option exits 2. `--frame NEW_PATH` writes the most recently completed 256×240 RGB PPM image without overwriting an existing file, and fails if no frame has completed. `--audio NEW_PATH` captures a maximum of 30 seconds as 44.1 kHz mono 16-bit PCM WAV, also without overwrite; `audio_truncated` reports exceeding the limit. `--video NEW_PATH` samples completed frames as Y4M, with `--video-fps` (1–60, default 10), `--video-frames` (1–3600, default 300), and `--video-start` (modeled CPU cycle, default 0). The JSON reports saved frames, limit, truncation and last cycle. The first sample is delayed until a frame completes; audio and video are separate files and are not guaranteed to align exactly. `--cycles`, `--until`, multiple inspections, cancellation events, and witnesses are not supported by this target.

`--controller1 MASK` sets the initial static first-controller state. `--controller-event STEP:MASK` is repeatable (up to 256 events), ordered by nondecreasing instruction step, and replaces that state immediately before the selected instruction boundary. Masks use bits 0–7 for A, B, Select, Start, Up, Down, Left, Right. The second controller is fixed at zero. These are emulated inputs and do not touch the physical keyboard. A stop condition is checked before an event at that boundary; `controller_schedule` reports scheduled, accepted and pending counts. The modeled controller upper read bits are a fixed `0x40` approximation, not general open-bus behavior.

The result includes the cartridge SHA-256, instruction and modeled CPU-cycle counts, PPU frame count, PC, registers, APU-write and OAM-DMA counts, audio sample count, capture and truncation flags, and `dmc_used` when the DMC memory reader has fetched a byte. One optional `--inspect ADDRESS:LENGTH` reads up to 4096 bytes of supported CPU RAM or ROM without side effects; it cannot span an unmapped/device region. The cartridge is opened read-only. A CPU stop reports the unsupported opcode or bus access, instruction address and relevant bus address. Faulting instructions do not increment the instruction count; register changes are rolled back. This diagnostic does not reproduce cycle-level bus activity, general open-bus behavior or reset timing.

## Supported cartridge and memory

The loader accepts strict, exact-size **iNES 1.0 mapper 0** images with one or two 16 KiB PRG-ROM banks and zero or one 8 KiB CHR-ROM bank. It also accepts a limited **NES 2.0 mapper 0/submapper 0** form with one CHR-ROM bank, no declared cartridge RAM, NTSC or multi-region timing metadata, and an unspecified or standard-controller expansion setting. It rejects unsupported NES 2.0 metadata, other mappers, trainers, battery-backed RAM, four-screen memory, and trailing or truncated data. A 16 KiB PRG bank is mirrored into both CPU ROM windows; a 32 KiB image occupies both windows separately. iNES images with no CHR-ROM use 8 KiB CHR RAM. These restrictions are not claims that rejected images are invalid NES media.

The reset vector is read from `FFFC`–`FFFD`. The deterministic initial model sets A, X, Y and the 2 KiB RAM to zero, SP to `FD`, and flags to `24`; real console power-on state can differ. CPU RAM is mirrored through `1FFF`; PPU registers through `3FFF`; the cartridge occupies `8000`–`FFFF`. OAM DMA copies from supported CPU RAM or ROM and adds a modeled 513/514-cycle stall. The approximate NTSC APU implements pulse, triangle and noise synthesis, length/envelope/sweep/linear counters, frame IRQ, status reads, DMC direct DAC and sample fetch/loop/IRQ, and a filtered nonlinear mix. DMC fetches are serviced at instruction boundaries with a fixed four-cycle charge; OAM/DMC bus contention and exact DMA alignment are not modeled. Frame-sequencer reset delay, mixer/filter response, timer edge cases and bus-cycle accuracy are approximate. Other unsupported bus accesses fault. ROM-write faulting is a diagnostic restriction, not a model of physical cartridge bus conflicts.

The interpreter implements the 151 documented 6502 opcode encodings and addressing modes, including stack operations, BRK/RTI, and the indirect-JMP page-wrap behavior. Arithmetic remains binary even when the decimal flag is set. Undocumented opcodes fault before being counted. BRK is an interrupt instruction, not a stop command. CPU instruction cycle counts and branch/page-cross penalties drive three PPU dots per modeled CPU cycle, including the NTSC odd-frame skip when rendering is enabled. NMI and APU IRQs are delivered at instruction boundaries. Dummy bus accesses, PPU/CPU bus-cycle races and PPU startup write suppression are not modeled.

The PPU models register accesses, CHR and nametable mapping, palette aliases, buffered reads, vblank, and simplified sprite-zero hits. Its renderer approximates background, scrolling, up to eight sprites per scanline, priority, and a fixed RGB palette. It does not implement the original fetch pipeline, precise mid-scanline scroll changes, sprite overflow quirks, color emphasis, or composite output. Visible HUD/scrolling artifacts are known. A successful image is not evidence of a pixel-accurate or complete game.

Synthetic tests cover both NROM PRG layouts, NES 2.0 header validation, mirrored RAM, instruction flow, unsupported devices and opcodes, bounded stops, no-overwrite still/audio/video captures, controller latching, PPU mapping/buffering/NMI, simple rendering, and basic APU waveform, frame IRQ, DMC fetch, loop, address wrapping and IRQ. A separate CPU test checks all 151 documented opcode encodings are accepted and undocumented encodings rejected; exhaustively checks 262,144 ADC/SBC input and carry combinations; and tests representative addressing, stack/interrupt instructions, flags and page wrapping. Opcode acceptance is not exhaustive instruction conformance.

The optional `BOOTHUSH_NES_ROM` integration test uses the user's independently supplied Super Mario Bros. image with SHA-256 `0b3d9e1f01ed1668205bab34d6c82b0e281456e137352e4f36a9b2cfa3b66dea`. A title-screen run and a Start press produce different frames; a repeated Start run matches its full frame and JSON. A longer controlled comparison checks that right input changes RAM and the captured frame. The input is not redistributed. In observed runs the title screen and World 1-1 transition were recognizable, with movement, jumping and scrolling after scheduled inputs. A five-million-instruction run produced 87 sampled video frames and 379,783 WAV samples, including nonzero samples; a 25-million-instruction run reached its requested bound, accepted all eight events, and reported the 30-second audio cap. No listening or hardware-reference comparison was performed. These observations do not establish audio accuracy, a full playthrough, game compatibility, or hardware accuracy.
